# ADR-017 — Web demo API: sg-api as the single door to both agents, a blind comparison and votes

- **Status:** Proposed (2026-10-22): accepted after the live check in SMO-35 Task 11
- **Date:** 2026-10-22
- **Linear:** SMO-34 (web demo), SMO-35 (this API), SMO-36 (web app)
- **Deciders:** Alexander (decides) · Claude (drafts)

## Context
The master's jury will use a web demo of StoreGear (spec: `storegear-web/docs/superpowers/specs/2026-10-22-storegear-web-design.md`). Demo accounts see **both** agents answer the same question side by side: the n8n build (the official deliverable, n8n Cloud) and the Google Cloud build (Agent Runtime behind `sg-api`). Visible progress steps run while each agent works, and the jury votes on which answer is better **without knowing which agent is which** until the end of the conversation. Staff accounts without the demo flag use the Google Cloud agent only.

Constraints: role and identity come only from the verified login (ADR-014). PII is masked before any model sees it (ADR-015). The n8n webhook is protected by an HS256 token. Agent Platform access is restricted while this is built (2026-10-22), so everything is tested with fakes.

## Options considered
| Option | Pros | Cons |
|---|---|---|
| **A. `sg-api` calls both agents (chosen)** | One login, one rate limit, PII masked once for both; the n8n secret stays on the server; the A/B mapping never reaches the browser; n8n's steps are simulated on the server, so both columns look the same | `sg-api` does more; a compare costs two agent calls |
| B. The browser calls n8n and `sg-api` separately | Less server code | The n8n token or secret ends up in the browser; the blind is impossible (the network tab shows which URL answered); two rate limits, PII masked twice |
| C. n8n calls the Google Cloud agent too | — | Mixes the two builds being compared; the n8n plan has no room for it |

## Decision
**A.** New endpoints in `sg-api`:
- `GET /catalog/models` (public): display names of the staff manuals.
- `POST /compare` (demo only, SSE): both agents in parallel. A/B is drawn once per conversation and kept in Cloud SQL (`compare_conversations`). Steps carry no per-step time (n8n's would be invented and would give the blind away); each column has a real total.
- `POST /compare/{id}/vote`: one vote per question, never when a slot failed or after the reveal.
- `POST /conversations/{id}/reveal`: ends the conversation and returns the mapping.
- `POST /chat/stream`: the Google Cloud agent alone, with real per-step times. `/chat` keeps its JSON contract.

**n8n call:** a token signed by `sg-api` (HS256, `sub` = uid, role staff, 60 s expiry). The secret lives in Secret Manager (`n8n-jwt-secret`, accessor granted on that secret only) and in the n8n credential. It is rotated for this (generated by Alexander, never pasted anywhere).

**Steps (Google Cloud):** fixed labels that only move forward: Pregunta revisada (guardrails) → Buscando en los manuales (from the start of the agent call; the agent searches before its first model call) → Consultando precio y stock (only if called) → Redactando la respuesta. Without partial events the final text arrives in one event, so drafting time is counted under search. Partial events can be turned on (`STOREGEAR_PARTIAL_EVENTS=1`) after a live check.

**Failure:** each slot fails on its own, with a fixed text ("Este agente no ha podido responder ahora.") and a 150 s deadline; if Agent Runtime is unreachable, only its column fails.

## Consequences
- **Good:** the blind holds at the network level; the n8n secret never leaves the server; one rate limit and one PII mask for both agents. The votes and the real totals feed the SMO-29 comparison.
- **Bad / accepted trade-offs:** a compare costs two agent calls (demo accounts only). Votes are personal data tied to a uid: they are deleted once the SMO-29 report is written (runbook). n8n's steps are a schedule, not real events (stated in the thesis annex).
